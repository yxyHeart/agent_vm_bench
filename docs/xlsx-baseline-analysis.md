# XLSX 基准优化前耗时分析报告

> 日期: 2026-09-01 ｜ 对象: XLSX 文档基准, 优化前(全 stock: 发行版 CPython 3.12 + openpyxl 3.1.5 原样)
> 场景: 2核4G docker 容器, 单任务端到端 **257.5s**。数据来源: 15 个工具调用逐点计时(CALLTIMINGS 埋点)、py-spy 火焰图(9 步)、perf 采样(per-DSO/per-symbol)。

## 一、总账: 257.5s 花在哪

按"执行内容"归类(而非表面阶段), 三块分干净:

| 类别 | 耗时 | 占比 | 明细 |
|------|----:|----:|------|
| **openpyxl 全量加载** | **192.7s** | **74.8%** | 7 次调用: TP-04/05/07(内含 1 次 load)/09/10/13/14, 单次 20~30s |
| **LibreOffice 重算(TP-08)** | 62.6s | 24.3% | soffice 重算 ~16s + recalc.py 内部 2 次全量 load ~45s |
| 其余 I/O | ~2.2s | 0.9% | 读写文档/拷模板/读 JSON/流式导 CSV/断言 |

> 注意 TP-08 的 62.6s 里约 45s 其实是 openpyxl(重算后查错误 + 数公式两次全量加载),
> 若按真实执行者归类, openpyxl 占比升至 **~92%**。表面"重算是第二瓶颈"是错觉。

## 二、读/写全景: 全量加载 ×10, 流式 ×3, 写 ×1

对全部 recipe 命令与冻结脚本源码逐一盘点(含脚本内部):

```text
全量 load_workbook ×10:
  TP-04 模板(结构)   TP-05 副本(图表)   TP-07 增强输入
  TP-08 ×2 重算后查错误(data_only=True) + 数公式(False)
  TP-09 读公式       TP-10 读值         TP-13 校验(可编辑 1 次)
  TP-14 汇总
read_only 流式 ×3:  TP-12 导 CSV ×1 + TP-13 校验内 ×2   (1.7s 级, 忽略)
Workbook.save   ×1:  TP-07 增强输出(全流程唯一写)
```

关键结构: **同一份 123.5MB / 12.3 万行 / 250 万格工作簿被完整解析 10 次**, 每次都是
独立 `python3` 进程(`docker exec`), 内存对象树用完即弃, 跨调用零复用。
10 × ~19s = 全流程的大头。

## 三、单次加载为什么 ~20s: CPU 画像

perf(per-DSO) + py-spy 火焰图对单次全量加载的画像:

| 层 | 占比 | 说明 |
|----|----:|------|
| libpython(CPython 解释器) | **87%** | 逐条执行 openpyxl 的 Python 字节码 |
| libexpat(XML C 解析器) | 6.1% | 其中 top 命名函数 doContent 仅 0.74%, 余为内联碎片 |
| _elementtree | 3.6% | expat→Element 的 C 桥 |
| libz / libc | ~3% | 解压与杂项 |

**~190B 条指令 / IPC 2.5 / 无 memory stall / syscall 占比 ~0.07%**——CPU 执行效率不差,
纯粹是指令量爆炸。火焰图热点全部是每格一次的 Python 协议动作:

```text
parse_cell            ×250 万次   每次打包一个 5 键 dict 返回
coordinate_to_tuple   ×250 万次   切片+反转+字典查找解 "AB123"
parse_row / bind_cells ×10 万次   行装配 + 从 dict 逐键取 5 次再建 Cell
Cell.__init__          ×250 万次   构造函数 + 属性赋值 + 每格复制 StyleArray
```

地板测量进一步钉死归属: 同一 123MB sheet 的**纯 iterparse 空循环(expat+Element 创建,
零 Python 处理)只要 7.6s** → 20s 中约 **12s 是"Element→Cell 模型转换"的纯 Python 开销**,
即每格 ~5µs 的解释器协议税 × 250 万格。

三条相互印证的旁证:

1. **全量 vs 流式 12× 差距**: 同一份文件, `read_only=True`(TP-12)1.7s vs 全量(TP-09)20.9s——
   慢的不是读文件/解压/解析 XML, 是"把每个单元格实例化成 Python 对象树"这一步。
2. **数据规模线性放大**: 每 Cell 成本固定 µs 级, 12.3 万行 × 25 列 → 单次 20s;
   千行级小表单次 <0.1s, 冗余 10 次也无感——本基准的量级把"每格固定税"放大成主瓶颈。
3. **硬件侧无处着力**(已实测排除): NUMA 绑核只压尾不提峰(无 stall); 多线程被 GIL 锁死
   (87% 时间在 libpython); SVE 进不了 expat(char-by-char 状态机无向量化循环,
   且整个 libexpat 才 6%)。瓶颈在软件形态, 不在微架构。

## 四、TP-07(51.0s)与 TP-08(62.6s)拆解

两个最重的调用单独拆:

**TP-07 原子增强 = load 20s + 小表修改(建 Executive_Summary/公式/图表/样式) ~6s + save 25s**。
save 侧同样是 250 万格的逐格 Python 序列化(etree_write_cell)+压缩——读和写各交一次"每格税"。

**TP-08 = soffice 重算 ~16s + recalc.py 两次全量 load ~45s**。重算本身(soffice C++ 引擎
读入 123MB+重算 36 个公式+写出)是负载固有成本, 动它就是换被测对象; 而 45s 的两次加载
与其余 8 次同质——同一个"每格税"问题的组成部分。

## 五、结论: 瓶颈的准确表述

> **为了处理约 250 万个 Cell, CPython + openpyxl 执行了约 1900 亿条指令——
> 其中约 6 成是"每个单元格都要走一遍"的 Python 对象协议税
> (方法调用/中间 dict/字典查找/构造函数), 而同样的 XML 数据经 C 解析器
> 直接消费只要 7.6s。**

优化空间的分层结构(对应后续各优化层的靶子):

| 靶子 | 量级 | 对应优化方向 |
|------|------|--------------|
| 10 次重复解析同一文件 | ~80s | 多次读缓存(命中后 ~4s/次) |
| 每格协议税(解析侧) | ~12s/次 | 融合原生循环(每格 Python 调用链 → C) |
| 每格协议税(写侧, 仅 TP-07) | ~25s | writer 原生化(未做, 下一步) |
| soffice 重算 | ~16s | 负载本身, 不动 |
