# XLSX 第二轮优化：从解释器层削减指令量

> 日期: 2026-08-29 ｜ 场景: 2核4G docker 容器, XLSX 文档基准, recipe 冻结
> 结论: **今日同条件 A/B: 160.7s → 116.6s (-27.5%), Success 100%**; 对最初无缓存基线 259s 累计 **-55%**

## 一、背景：为什么这一轮不再调 CPU，而是让 CPU 少干活

PMU 数据给出的画像非常明确:

| 指标 | 当前表现 | 含义 |
|------|------:|------|
| Instructions | ~190B | 真正的问题: 指令数太多 |
| IPC | ~2.50 | CPU 执行效率不差 |
| syscall | ~0.07% | 不是 I/O 瓶颈 |
| libpython 占比 | ~87% | CPython 解释器是第一瓶颈 |
| libexpat | ~6.5% | XML 解析器反而不是大头 |

为了处理约 250 万个单元格(10 万行 × 25 列), CPython + openpyxl 执行了约 1900 亿条指令。缓存(第一轮)已经消灭了"重复解析", 但每次真正的解析、每次命中后的重建、每次存盘, 仍然按"每个单元格一套 Python 对象协议"来执行。这一轮的目标就是把这些固定税逐项砍掉——不是让每条指令更快, 而是不执行它们。

## 二、四项优化

### 优化1: 解析期间关闭循环垃圾回收

**背景。** 加载一个 250 万格的工作簿, 会让堆上的存活对象持续增长到几百万个。CPython 的循环垃圾回收器每隔一段分配量就醒来一次, 把这些仍然存活的对象扫描一遍——而它们几乎不构成垃圾循环。纯 CPU 浪费, 且对象越多扫得越久。

**方法。** 在"完整解析""缓存命中重建""缓存填充提取"三个阶段临时关闭垃圾回收, 结束后恢复原状。回收的是"扫描存活对象"的浪费, 不影响任何业务对象的生命周期。

**收益。** 单次完整解析 **-3.9s**(25.2s → 21.4s)。

### 优化2: 单元格对象跳过构造函数, 直接填充槽位

**背景。** 每个单元格对象的标准构造要做一轮已知道答案的初始化(默认值、类型判断、样式包装), 之后每个字段再被覆盖一遍。250 万次 × 每次若干条解释器指令, 就是几亿条指令。此外每个单元格还会**复制一份**样式数组, 而样式是只读的值对象, 完全可以共享。

**方法。** 两条路径同时替换为"直接构造 + 槽位直填": ① 缓存命中后的重建; ② openpyxl 自己的解析装配路径。样式改为共享样式表条目, 不再逐格复制。带版本与源码特征校验, 不匹配或出错时自动退回原生路径。

**收益。** 单次完整解析再 **-3.9s**(与优化1叠加: 25.2s → 18.8s); 缓存命中重建 **~5s → 2.15s(约 2.3×)**。

### 优化3: 删除存盘后的无效缓存填充

**背景。** 第一轮在"存盘"后顺手把内存里的工作簿填进缓存, 为了让"存盘→再读"命中。但重新核对 recipe 后发现: 整条流程里**只有一处 openpyxl 存盘**(增强脚本), 它的产物马上被 LibreOffice 重算整文件改写——刚填的缓存指纹立刻失效, **永远不会被任何人命中**。每次白付几秒。

**方法。** 撤掉存盘挂钩。缓存只由"加载"动作填充, 语义不变(此前报告里"存盘→再读链命中"的描述对应旧版 recipe; 现版里 TP-05 只读不写, 命中链完全来自内容指纹, 不受影响)。

**收益。** 增强步骤 **-2~3s**, 且不再产生注定作废的 CPU 与磁盘写。

### 优化4: 存盘改走 lxml 序列化(读取路径不动)

**背景。** 此前实验证明"lxml 读 worksheet 慢 59%", 但那只对**读**成立。openpyxl 的**写**路径是独立一套: 装了 lxml 后自动切换到 lxml 的增量序列化, 且**读路径在源码里无条件使用标准库**——装 lxml 不会碰读。之前"lxml 全没用"的结论扩大化了。

**方法。** 镜像里离线安装 lxml(构建机无外网, 从本机取 aarch64 wheel 传入)。不改任何代码, openpyxl 导入时自行切换; 留有原厂开关可随时切回对照。

**收益。** 全量存盘 **24.98s → 22.67s(-9.3%)**。

## 三、验证

### 正确性(逐格指纹, 非抽样)

把全部 2,501,211 个单元格的(坐标/值/类型/样式/批注/超链接)做成指纹, 在 8 种组合下比对——纯净 openpyxl、第一轮缓存、第二轮默认、各开关单独关闭、两种存盘引擎的产物再读回——**md5 全部一致**。LibreOffice 对 lxml 存盘产物做完整公式重算: `success, 0 errors, 36 formulas`。

## 四、剩余瓶颈(下一轮 P1 方向)

| 剩余大头 | 当前耗时 | 对应方向 |
|----------|----:|----------|
| TP-07 存盘: 250 万格 XML 序列化+压缩 | 22.7s | 大表 ZIP 直通(不解压不重排, 字节级搬运) |
| TP-08 重算后文件首次双读 | ~39s(两次) | Raw 大表懒加载/不物化 |
| TP-08 LibreOffice 重算 | ~16s | 负载本身, 不动 |
| 首任务冷解析 | ~25s | 同 Raw 懒加载 |

即: 缓存把"重复解析"消灭后, 剩下的是"每次解析都太重"——只有让 Raw 大表根本不物化 250 万个单元格对象, 才能再下一个量级(向 100s 以内打)。
