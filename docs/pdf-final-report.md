# PDF 批处理基准性能优化 — 汇报

> 日期: 2026-08-31
> 环境: Kunpeng 920B 服务器 (ARM aarch64), 2核4G 容器, pypdf + Poppler/Pillow 软件栈
> 任务: OF-306 联邦就业申请表批量填充基准 (10 份申请 × 填表/渲染/校验全流程)
> 优化原则: 只做底层库 + CPU 层面的通用优化, 对上层业务流程零侵入, 成果可平移到未来任何新流程

## 一、总体成果

| 指标 | 优化前 | 优化后 | 降幅 |
|------|-----:|-----:|-----:|
| 端到端耗时 | 11.98s | **10.96s** | **-8.5%** |
| 任务成功率 | 100% | 100% (60/60) | — |

两项通用优化: 系统压缩库替换 zlib-ng (**E2E -0.89s**, 探针实测 zlib 内部耗时 -58%) + PDF 库运行时协议继承移除 (**E2E -0.22s**)。全部为库层/系统层改动, 不修改任何业务脚本与流程编排。

## 二、优化方法: 用数据定位, 逐项实验排除

工作方法是"先剖析、再动手": 先用采样剖析器把 11.98s 拆到函数级, 再对每个候选方向做同日背靠背 A/B 实验。剖析发现: 单份文档处理 215ms 中, 真正的业务操作 (填 23 个字段) 只占 **1.5%**, 其余 98.5% 是软件库的基础设施开销——这决定了优化主战场在底层库而非业务层。

## 三、成功的优化

### 优化 1: 系统压缩库替换为 zlib-ng (E2E -0.8s) ✅

**背景**: 剖析显示 PNG 图片压缩 (zlib 库) 是原生代码层最大 CPU 消耗——渲染出的每一页图片保存为 PNG 时都要过一遍 deflate 压缩, 30 页/批的压缩开销占了端到端的可观比例。系统自带的 zlib 诞生于上世纪 90 年代, 核心算法 (哈希链查找、数据块拷贝、校验和计算) 全部是**单字节标量实现**, 二十年没有为现代 CPU 的向量指令做过重构。

**zlib-ng 的 NEON 优化具体在哪**: zlib-ng (zlib next generation) 把 deflate 压缩的四个热点环节全部重写为 ARM NEON 128 位向量实现 (源码 `arch/arm/` 目录):

1. **匹配比对 (compare256)** —— 压缩的核心操作是"比较两个位置的数据最长能匹配多少字节", 原版逐字节比较; NEON 版用 `vld1q_u8` 一次加载 16 字节, 异或后用硬件 CTZ 指令 (Count Trailing Zeros) 一条指令定位第一个差异字节——**单次比对吞吐 16 倍**, 这是图像数据 (大片相同颜色) 收益最大的路径。
2. **哈希表平移 (slide_hash)** —— 滑动窗口前移时要把整张哈希表的表项统一减一个常数, 原版逐项 16 位减法; NEON 版用饱和减法指令一次处理 **64 个表项** (`vqsubq_u16_x4`), 窗口维护成本下降一个数量级。
3. **块填充 (chunkset)** —— 压缩中大量"把短模式复制铺开"的操作 (RLE 类匹配), 原版逐字节复制; NEON 版用 128 位寄存器查表排列一次铺 16 字节, 消除压缩输出路径上的字节级循环。
4. **校验和 (adler32)** —— 每 5552 字节一次的校验和更新, 原版是逐字节双累加 (有数据依赖的串行加法, 无法流水); NEON 版用 4 路向量累加器 + 64 项 tap 系数表把串行依赖链拆成并行车道。

此外 zlib-ng 还有现代 C 重写 (分支提示/内联提示/减少全局变量别名) 与 **ARM CRC32 硬件指令**支持。我们编译时叠加了鲲鹏专属参数 `-O3 -mcpu=tsv110`。

**做法**: 从源码编译 zlib-ng 2.2.4 (兼容模式, 对外接口与 zlib 完全一致), 部署于独立目录 `/opt/zlib-ng`, 通过容器级 `LD_PRELOAD` 让所有进程 (Python/Pillow/Poppler) 无感知地使用它——不覆盖任何发行版文件, 删除一个环境变量即可完全回退。部署时曾抓到一个坑: 最初放在 `/usr/local/lib` 期望链接器优先生效, 实测**并未生效** (进程仍加载系统 zlib, 端到端假持平); 修正部署方式后加入"进程内实际加载路径"断言, 确保优化真正在运行。

**效果**:
- 压缩微基准 (真实图像数据 2.3MB): 默认压缩级别提速 **51%** (25.1→12.4ms), 快速级别提速 **56%**
- Pillow PNG 保存: 每页 **40.0→25.5ms (-36%)**
- 端到端: 11.98 → 11.18s
- 输出的 PNG 文件字节不同 (压缩路径变了) 但**解码像素完全一致**, 下游逐像素校验 100% 通过

**耗时占比实测** (自研 `libzcount.so` 探针库: 以 LD_PRELOAD 方式拦截 zlib 的 deflate/inflate 等入口, 精确计数每次调用并累计耗时, 进程退出时落盘; 修正了容器 pid 复用导致日志覆盖的漏采问题后, 于真实基准上精确计量):

| 指标 | 替换前 (系统 zlib) | 替换后 (zlib-ng) | 变化 |
|------|-----------------:|----------------:|-----:|
| deflate (PNG 编码 + PDF 流压缩) | 1,326ms / 33,048 次 | 568ms / 33,056 次 | **-57%** (单次 40.1→17.2µs) |
| inflate (PDF 流解压 + PNG 解码) | 139ms / 20,347 次 | 53ms / 20,347 次 | **-62%** |
| **zlib 合计** | **1,465ms (占 E2E 12.3%)** | **620ms (占 5.6%)** | **-58%** |

调用次数两组完全一致 (工作负载确定性), 唯一变量是压缩库本身。数据自洽性: zlib 内部节省 845ms, 端到端实测节省 ~890ms, 账目闭合 (95% 由 zlib 内部提速直接贡献)。调用特征上, Pillow/pypdf 均为流式小块调用 (每页 PNG 约 1,000 次、单次仅 17~40µs), 这种高频小包调用场景正是 zlib-ng 向量化实现 (一次比对 16 字节) 相对逐字节实现收益放大的原因。

（本节数据已由上方"真实基准精确计量"表取代——早期缩减负载对照 (91.2→42.3ms, -54%) 与微基准 -51% 方向一致, 但当时探针存在 pid 复用漏采问题, 以全量精确数据为准。）

### 优化 2: pypdf 库运行时协议继承移除 (E2E -0.22s) ✅

- **背景**: 剖析发现 PDF 库每次复制文档要执行 **6.2 万次慢速类型检查** (占单次复制 11%)。根因: 库的两个核心类出于类型标注目的继承了 Python 的 Protocol 基类——该机制本应只供开发工具静态分析使用, 运行时继承会让每次类型判断都走一遍复杂的协议核对流程, 相当于纯粹的"运行时税" (实测纯 isinstance 慢 5.8 倍)。
- **做法**: 去掉两处运行时 Protocol 继承 (共 **2 行**改动, 类型标注不受影响)。此修复对使用该库的一切场景 (合并、加水印、旋转、拆分等) 通用有效, 具备向开源社区回馈的条件。
- **效果**: 单次文档复制耗时 **186.4 → 159.5ms (-14.4%)**; 端到端 11.18 → **10.96s**。用冻结的原始业务脚本回归, 输出文件**逐字节一致** (MD5 校验)。

## 四、未成功的探索 (每项含背景/做法/效果与原因分析)

### 探索 1: 压缩库热点函数 SVE 向量化 (自研) ❌ (E2E 零收益)

- **背景**: zlib-ng 的向量化实现基于 NEON (128-bit)。服务器 CPU 实际支持 SVE 指令集 (实测向量长度 256-bit, 为 NEON 的 2 倍), 且 zlib-ng 上游没有 SVE 后端——若将最热的压缩匹配比对函数换成 SVE 实现, 理论上单次比对吞吐可翻倍。
- **做法**: 手写该函数的 SVE 版本 (一次比对 32 字节 + 谓词定位首个差异字节), 与 NEON 版做 20 万组随机用例交叉验证保证语义一致; 再以函数级编译开关 + CPU 能力运行时探测的方式集成进 zlib-ng, 反汇编确认 SVE 指令真实进入二进制; 最后在真实基准上与 NEON 版背靠背对照。
- **效果与原因**: 孤立微基准 SVE 版快 **1.8 倍**, 但真实基准三变体对照 (同探针、同负载、精确计量):

| 指标 | 原版系统 zlib | zlib-ng (NEON) | zlib-ng (SVE) |
|------|------------:|--------------:|--------------:|
| deflate 耗时/任务 | 1,326ms / 33,048 次 | 568ms / 33,056 次 | 577ms / 33,056 次 |
| 单次 deflate | 40.1µs | 17.2µs | 17.5µs |
| inflate 耗时/任务 | 139ms / 20,347 次 | 53ms / 20,347 次 | 53ms / 20,347 次 |
| **zlib 合计/任务** | **1,465ms (E2E 的 12.3%)** | **620ms (5.6%)** | **630ms (5.7%)** |
| **端到端** | 11.89s | **11.00s** | 11.12s |

SVE 版与 NEON 版在真实端到端上**零差异** (11.12 vs 11.00s, 噪声内)。**原因**: 该函数虽是最热内循环, 但在整个压缩流程中占比有限 (图像数据下压缩时间大头在哈希链遍历与哈夫曼编码); 且实测本机 256-bit SVE 吞吐仅比 NEON 高 8%——疑为 2×128-bit 拆分执行而非真 256-bit 数据通路。结论: 在当前硬件 (SVE1、无 SVE2) 与负载上不采纳, 待真 256-bit 通路的下一代硬件 (如 Neoverse V2) 可重估。

### 探索 2: JPEG / 字体库优化 ⏭️ (有据排除, 未立项)

- **背景**: 渲染链路理论上可能经过 libjpeg (PDF 内嵌 JPEG 图片解码) 和 FreeType (字体光栅化), 两者都有 ARM 优化版可换。
- **做法**: 不做盲目替换, 先做证据检查——用 `pdfimages -list` 对模板做嵌入图像清单检查。
- **效果与原因**: 清单显示模板嵌入图全部为 32×32 原始数据 (无任何 jpeg/jpx 编码条目), libjpeg 确认不在路径上; 字体库无独立热点证据。**结论**: 按 ROI 暂缓, 若未来任务语料含 JPEG 图片再立项。

**排雷价值**: SVE 项验证了"孤立微基准收益 ≠ 真实收益"——集成实测是唯一可信判据; JPEG/字体项则示范了"先取证再立项"的低成本排除法。

## 五、质量保障

- **一致性回归**: 每项优化双重验证——(1) 冻结业务脚本输出与优化前逐字节一致 (MD5); (2) 逐像素校验 100% 通过。
- **部署可回退**: zlib-ng 以独立目录 + 环境变量方式部署, 单命令回退; pypdf 补丁 2 行, 构建期自动断言生效。
- **防测量假象**: 所有实验均带"优化确实在运行"的进程内断言 (曾借此抓到一次部署未生效导致的假持平)。
- **耗时归因工具**: 自研 `libzcount.so` 探针库 (LD_PRELOAD 拦截 + 精确计时), 可对任意 workload 量化 zlib 的调用次数与时间占比, 用于优化收益的事前评估与事后验证。
