# XLSX 第三轮优化：大表不再物化

> 日期: 2026-08-29 ｜ 场景: 2核4G docker 容器, XLSX 文档基准, recipe 冻结
> 结论: **116.6s → 70.2s(-39.8%), Success 100%, 复跑 70.2s**; 对无缓存基线 259s 累计 **-72.9%**

## 一、背景：缓存命中之后，剩下的钱花在哪

第二轮结束时每个任务 116.6s, 逐调用计时显示剩余大头全部压在"必须真解析"的场合:

| 剩余热点 | 耗时 | 在做什么 |
|----------|----:|----------|
| TP-07 存盘 | 22.7s | 把 250 万格重新 XML 序列化 + 压缩 |
| TP-08 重算后首次双读 | ~39s | 两次从头解析(每次 ~19s) |
| TP-04 首次冷解析 | ~25s | 一次从头解析 |

共同点: 全部在为 **Raw_Sample 这张 12.3 万行大表**付钱。而核查 recipe 后发现, 整条流程里 15 次工具调用**没有任何一次真正读 Raw 的数据区**——检查结构只看行数列数和表头, 校验脚本显式跳过 Raw, 增强脚本只改小表。openpyxl 却在每次加载时老老实实把 250 万个格子全部变成 Python 对象。

于是这轮的问题是: **能不能根本不建这 250 万个对象?**

## 二、方法: 让大表"懒"下来

### 2.1 加载: 字节级体检, 合格就跳过

加载时把大表的 XML 整块读出(解压仅 0.17s), 用 C 速度的字节扫描做一次"体检", 判定这张表是否**简单表**:

- 只有数值/文本格, 没有公式、错误值、布尔、日期型格;
- 每格都有坐标和显式属性, 没有自闭合、没有富文本内联串、没有 XML 转义;
- 维度声明(A1:Y100001)与行结构完整。

合格 → 只解析表的"头部+尾部"(视图、列宽、筛选、边距、合并单元格等全部保留), 表体(250 万格)原样字节留存, 顺带物化第 1 行表头; 不合格 → 走原生完整解析, 行为与官方 openpyxl 完全一致。LibreOffice 重算后的文件是"共享字符串"形态(t="s"), 体检同样放行——文本值改查共享字符串表。

### 2.2 访问: 元数据即时答, 真访问才物化

- 行数/列数: 体检时已从维度声明取得, 读属性零成本;
- 读表头(第 1 行): 已物化, 零成本;
- 一旦真碰到数据区(任何第 2 行以下的格子、全表遍历): 触发**快速物化**——用字节级正则一次提取全部格子, 直接构造对象(第二轮的直填槽位技术), 数值/文本/日期格式转换逐条复刻官方逻辑。物化结果与官方解析**逐格一致**(下方 md5 验证)。任何意外(计数对不上等)自动回退官方解析器, 正确性兜底。

### 2.3 存盘: 原始字节直通

TP-07 的存盘此前要把 250 万格重新序列化。现在: 增强脚本只改了小表, Raw 从头到尾没被碰过——存盘时直接把它的**原始压缩字节**搬进新文件(低压缩级, 123MB 约 0.5s), 不再走"250 万对象 → XML → 压缩"的整条流水线。共享字符串形态的表(重算产物)不满足直通条件, 保守回退为"先物化再正常写", 该路径在本 recipe 中不会触发。

### 2.4 缓存协同: 快照缩到 MB 级

磁盘缓存照旧, 但大表在快照里只存一个"懒标记"(即使当次进程已物化过也只存标记), 快照从 58MB 缩到 MB 级, 命中重建进入亚秒级; 命中后大表的字节与元数据从源文件重新读取(内容指纹保证一致性)。

## 四、剩余瓶颈

| 项 | 耗时 | 说明 |
|----|----:|------|
| TP-08 LibreOffice 重算 | ~16s | 负载本身, 不动 |
| TP-08 两次物化+遍历 | ~17s | 重算校验确实要扫全表找错误串/公式, 物化是保底正确的代价 |
| TP-04 物化 | 6.5s | 结构检查读前 24 行触发; 可做"窗口化部分物化", 收益 ~5s, 复杂度高暂缓 |
| TP-13 校验逻辑 | ~4s | verify 脚本自身 Python 逻辑, 冻结 |

再往下打只剩两类: 窗口化物化(~5s)与 recalc 校验的原生加速(~10s), 均属 P2。
